# 设计模式

## 概述

> 面向对象的 23 种经典设计模式(GoF),按创建型 / 结构型 / 行为型分类,重点标注 Spring 框架里的落地。设计模式不是为了炫技,而是为了「可维护、可扩展」,理解场景比死记结构更重要。

## 核心知识点

### 创建型:如何创建对象

| 模式 | 场景 | 要点 |
|------|------|------|
| **单例 Singleton** | 全局唯一实例(配置、连接池) | 懒汉/饿汉/双检锁/枚举 |
| **工厂方法 Factory** | 延迟到子类决定创建哪个对象 | Spring 的 `BeanFactory` |
| **建造者 Builder** | 参数多、构造复杂 | 链式 `new User.Builder().name(...).build()` |
| 原型 Prototype | 拷贝对象 | `Cloneable` |

**单例的四种写法**(从差到好):

```java
// 1. 饿汉式:类加载即创建,简单,但可能浪费
public class Singleton1 {
    private static final Singleton1 INSTANCE = new Singleton1();
    private Singleton1() {}
    public static Singleton1 getInstance() { return INSTANCE; }
}

// 2. 懒汉式(线程不安全,别用)
// 3. 双检锁(volatile 防指令重排,较常用)
public class Singleton3 {
    private static volatile Singleton3 INSTANCE;
    private Singleton3() {}
    public static Singleton3 getInstance() {
        if (INSTANCE == null) {
            synchronized (Singleton3.class) {
                if (INSTANCE == null) INSTANCE = new Singleton3();
            }
        }
        return INSTANCE;
    }
}

// 4. 枚举(推荐,天然线程安全、防反序列化破坏)
public enum Singleton4 {
    INSTANCE;
    public void doSomething() {}
}
```

### 结构型:如何组织对象

| 模式 | 场景 | 要点 |
|------|------|------|
| **适配器 Adapter** | 兼容不匹配的接口 | `InputStreamReader` 包装流 |
| **代理 Proxy** | 控制访问、增强 | Spring AOP 的核心 |
| **装饰器 Decorator** | 动态加功能 | `BufferedReader` 包装 `Reader` |
| 门面 Facade | 统一复杂子系统的入口 | 一个 Service 聚合多个调用 |
| 组合 Composite | 树形结构(目录、菜单) | |

**代理 vs 装饰器**:代理关注「控制/增强访问」(鉴权、日志、事务),装饰器关注「叠加功能」,两者结构相似但意图不同。

### 行为型:对象如何协作

| 模式 | 场景 | 要点 |
|------|------|------|
| **策略 Strategy** | 多种算法可切换(支付方式、排序) | 接口 + 多个实现 + 注入选择 |
| **观察者 Observer** | 一对多通知(事件发布) | Spring `ApplicationEvent` |
| **模板方法 Template** | 固定骨架、步骤可变 | Spring `JdbcTemplate`、`RestTemplate` |
| **责任链 Chain** | 多个处理器依次处理(拦截器、过滤器) | Servlet Filter、Spring Interceptor |
| 迭代器 Iterator | 遍历集合 | `Iterator` |

## 示例

**策略模式**(支付场景,替代一堆 if-else):

```java
public interface PayStrategy {
    void pay(int amount);
}

public class AlipayStrategy implements PayStrategy {
    public void pay(int amount) { System.out.println("支付宝支付 " + amount); }
}
public class WechatStrategy implements PayStrategy {
    public void pay(int amount) { System.out.println("微信支付 " + amount); }
}

// 用枚举 + 工厂避免 new 一堆类,或用 Spring 注入 Map<String, PayStrategy>
public class PayService {
    private final Map<String, PayStrategy> strategies = Map.of(
        "alipay", new AlipayStrategy(),
        "wechat", new WechatStrategy()
    );
    public void pay(String type, int amount) {
        PayStrategy s = strategies.get(type);
        if (s == null) throw new IllegalArgumentException("不支持的支付方式");
        s.pay(amount);
    }
}
```

在 Spring 里更优雅:把所有 `PayStrategy` 实现类注入到一个 `Map<String, PayStrategy>`(key 是 bean 名),通过类型名直接取。

**观察者模式 + Spring 事件**(解耦下单后的一连串操作):

```java
// 1. 定义事件
public record OrderCreatedEvent(Long orderId, Long userId) {}

// 2. 下单后发布事件,Publisher 不关心谁在监听
@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;
    public OrderService(ApplicationEventPublisher publisher) { this.publisher = publisher; }

    @Transactional
    public void createOrder(Order order) {
        // 保存订单...
        publisher.publishEvent(new OrderCreatedEvent(order.getId(), order.getUserId()));
    }
}

// 3. 监听者:发短信、加积分、通知库存,互不耦合,可独立增减
@Component
public class OrderListener {
    @EventListener
    public void onOrderCreated(OrderCreatedEvent e) {
        System.out.println("订单 " + e.orderId() + " 已创建,通知用户 " + e.userId());
    }
}
```

`OrderService` 无需知道发短信/加积分的存在,后续新增监听者也不改下单逻辑——这就是观察者模式的解耦价值,Spring 的 `ApplicationEvent` 把它做成了开箱即用。

## 常见问题与坑

- **为用而用**:简单逻辑硬套模式,代码反而更难读。先用直白代码,确需扩展再重构
- **单例的线程安全**:懒汉式不加锁会出多个实例,生产优先用枚举或 Spring 单例 bean
- **策略模式里 if-else 没消除干净**:直接把策略对象放 Map,别再用 if-else 判断类型
- **代理模式混淆装饰器**:二者结构一样,靠意图区分,别在命名上纠结
- **过度设计**:一上来就抽象 Factory + Strategy + 一堆接口,不如先满足需求再演进
